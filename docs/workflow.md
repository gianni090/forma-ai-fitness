## Цель первого спринта

К концу спринта на тестовом стенде создаётся и сохраняется профиль пользователя, а интеграционный вызов по его обезличенным параметрам формирует структурированный недельный план с опорой на каталог не менее 80 упражнений.

Бэклог: Т1 — Криворучко, 2 чел.-дн.; Т2 — Бескоровайный, 3; Т3 — Дышко, 2,3333; Т4 — Бескоровайный, 1,75; Т5 — Несмачный, 2; Т6 — Криворучко, 3; Т7.1 — Бескоровайный, 2. Начальный статус всех элементов — «не начата». Для Т3 и Т4 сохраняются ограничения исследования 5 и 4 чел.-дн. соответственно.

## Definition of Done

1. Каждый элемент бэклога имеет результат, подтверждённый критериями приёмки, ссылкой на PR и проверками.
2. Все замечания ревью устранены, нужные одобрения получены, успешные проверки относятся к последнему коммиту; изменения слиты в `main`.
3. Профиль сохраняется и открывается повторно, неверные значения отклоняются; каталог содержит не менее 80 валидных записей.
4. Формат AI-ответа проверяется; запрещённая правилами рекомендация блокируется. В репозитории нет секретов и реальных персональных профилей.
5. Т3 и Т4 закрываются протоколом исследования и решением. Отрицательный результат допустим для разведки, но блокирует зависящую от него продуктовую цель до согласования другого подхода.
6. Версии промпта, каталога и контрольных примеров зафиксированы. Для AI-изменений приложено сравнение с базовой версией; целевые значения не выдаются за уже измеренные результаты.
7. Результат продемонстрирован, блокирующие дефекты отсутствуют, документация и доска обновлены. Неготовая работа возвращается в бэклог с остаточной оценкой; спринт не продлевается.

## Ветки и коммиты

`main` содержит проверенную версию. Для одного проверяемого изменения создаётся короткая ветка от актуальной `main`: `<type>/<task>-<short-slug>`. Типы: `feat`, `fix`, `test`, `docs`, `spike`. Примеры: `feat/t01-profile-api`, `spike/t03-llm-evaluation`, `test/t07-2-safety-regression`, `docs/lr4-team-workflow`. Ветка для подзадачи использует дефис вместо точки. Идентификатор `lr4` разрешён для организационной документации лабораторной.

Коммит: `<type>(<scope>): <действие и результат> [<task>]`. Примеры: `feat(profile): добавить проверку параметров [T01]`, `docs(workflow): описать правила ревью [LR4]`. Коммит содержит одно связное изменение; сообщение объясняет результат. `.env`, ключи, пароли, персональные профили и журналы пользователей не коммитятся. Изменение схемы БД сопровождается миграцией и проверкой сохранения данных.

## Pull request и одобрения

PR открывается в `main`. В описании указываются задача, изменение поведения, критерии приёмки, выполненные проверки, затронутые данные/промпты и необходимость миграции. Для незавершённой работы используется draft; наличие draft PR не означает, что правила уже приняты в `main`.

Обычное изменение требует одного одобрения другого участника. Изменение AI-логики, правил безопасности, авторизации, доступа к данным или миграций требует двух одобрений разных участников, не являющихся автором: одно по предметной области/данным, другое по качеству и интеграции. Если назначенный специалист — автор, его заменяет другой компетентный участник; при отсутствии проверяющего слияние откладывается. Фитнес-эксперт оценивает планы, но не заменяет обязательное ревью кода.

Пример: PR Криворучко по профилю проверяет Несмачный, а при изменении доступа к данным дополнительно Бескоровайный; PR Бескоровайного по правилам проверяют Дышко и Несмачный; PR Дышко по AI — Бескоровайный и Несмачный. Автор не одобряет собственный PR. Существенные изменения после ревью требуют повторной проверки последнего коммита.

После успешного ревью и CI используется squash merge, затем рабочая ветка удаляется. Конфликты устраняет автор в своей ветке; после разрешения проверки повторяются. Прямые изменения `main` и её принудительная перезапись не входят в процесс. Число одобрений здесь — правило команды; программное применение через GitHub branch protection настраивается администратором отдельно.

## Проверки

Команды соответствуют текущим `package.json`, `README.md` и `.github/workflows/ci.yml`: `npm run db:generate`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:integration`, `npm run build`, `npm run test:ui`. Среда и переменные задаются по README. Интеграционные тесты и миграции выполняются только на выделенной тестовой базе. Существующий CI также выполняет production audit, применяет миграции и устанавливает Chromium. Живые платные AI-запросы не заменяют детерминированные проверки и запускаются отдельно при необходимости.

Для изменения только Markdown проверяются содержание, согласованность с планом и ссылки; новая функциональность тестами не имитируется. Если CI запускается для такого PR, перед слиянием его результат также проверяется. Этот документ не утверждает, что проверки уже пройдены или защита ветки настроена.

## AI-изменения и CACE

При изменении каталога, схемы профиля, промпта, модели или правил прослеживаются последствия для генерации, адаптации, формата, безопасности, времени, стоимости и интерфейса. В PR перечисляются затронутые контракты, фиксируются версии и результаты повторной оценки на контрольных примерах. Порог 0,70 используется только после определения и проверки способа его расчёта в Т4; самооценка модели не принимается без проверки метода. Изменение порога или целевых метрик требует согласования Product Owner и отражения в требованиях.

## Ежедневная синхронизация

Рабочий формат — до 15 минут в начале рабочего дня: что завершено и чем подтверждено, что делается дальше, какие есть препятствия. Scrum-мастер записывает решения, владельца действия и срок в командном журнале. Обсуждение деталей переносится на отдельную встречу. Статусы: «не начата» → «в работе» → «на проверке» → «готова»; блокировка фиксируется отдельной отметкой с причиной.

Если работа не помещается в спринт, команда пересчитывает остаток и влияние на зависимости, согласует объём с Product Owner и переносит незавершённую часть. Использование резерва фиксируется с причиной. Плановый календарь пересчитывается при изменении фактической доступности участников.
