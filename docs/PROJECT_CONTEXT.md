## Что обнаружил аудит

В исходной версии использовались Groq/Ollama и общий demo-user. Часть даты, имени, статистики и графика была зашита в интерфейс. На телефоне исчезала навигация, после старта скрывался журнал подходов, выводились только первые три дня программы. Обратная связь не участвовала в AI-генерации. Лимиты жили в памяти процесса, параллельные запросы могли создавать дубли сессий. Typecheck на чистой установке нуждался в генерации типов Next.js.

## Выполненные этапы

### 1. Основа и OpenRouter

- Node.js 24; Next.js 16.4.0, React 19.2.8, Prisma 6.19.3 по lockfile, Zod 4.
- `typecheck`: `next typegen && tsc --noEmit`.
- Groq SDK удалён. OpenRouter используется через серверный fetch; Ollama оставлен только для локальной разработки.
- Модель по умолчанию: `openai/gpt-oss-120b`; выбор через `OPENROUTER_MODEL`.
- JSON Schema, проверка структуры, числа дней, доступного оборудования, повторяющихся упражнений и целевых значений повторов/секунд.
- Безопасные сообщения об ошибках доступа, баланса, лимита, таймаута, пустого или обрезанного ответа. Тело ответа провайдера не выводится пользователю.
- Таймаут по умолчанию 90 секунд; маршрут допускает до 180 секунд.
- Последние 10 завершённых тренировок и 10 оценок включаются в следующую генерацию.
- Постоянные лимиты PostgreSQL: до 5 попыток в минуту и по умолчанию 10 в сутки на аккаунт; неудачные попытки учитываются. Одна выполняющаяся генерация, повтор успешного requestId возвращает готовый результат.

### 2. Аккаунты и данные

- Supabase Auth: регистрация, вход, подтверждение через callback, восстановление и изменение пароля, выход.
- Сервер проверяет пользователя через `auth.getUser()`; proxy обновляет auth cookies.
- Профиль: имя, недельная цель, часовой пояс и сохранённая AI-анкета.
- Во всех личных API проверяется владелец. Тела запросов ограничены, изменения защищены проверкой Origin.
- Demo-user доступен только при явном `AUTH_DEMO_MODE=true` вне production.
- Изменения одного пользователя сериализуются PostgreSQL advisory lock в транзакции.
- Все таблицы приложения и `_prisma_migrations` защищены RLS без клиентских политик; права `anon`/`authenticated` отзываются, если такие роли есть.
- Серверное DB-подключение использует владельца таблиц или доверенную роль BYPASSRLS. Изоляция аккаунтов для этого подключения обеспечивается серверными API.

### 3. Программы и тренировки

- Стартовая программа без AI, генерация, выбор активной программы, архив и восстановление.
- Показ всех дней, включая 7-й; редактор названия тренировки и упражнений, оборудования, целей, отдыха и заметок.
- Снимки параметров в сессиях сохраняют историю при изменении будущего плана; изменения записываются в версии программы.
- Начало и восстановление активной тренировки; параллельные старты создают одну сессию.
- Журнал подходов всегда доступен; повторы/вес и упражнения на время записываются корректно.
- UUID запроса предотвращает дубли подходов при повторной отправке; есть исправление и удаление.
- Таймер отдыха восстанавливается после перезагрузки.
- Завершение, отмена с сохранением истории, оценки нагрузки и комментарии.

### 4. Интерфейс, проверки и запуск

- Реальная статистика за неделю/месяц и объём как вес × повторы; отменённые тренировки исключаются.
- Часовой пояс пользователя применяется к календарным показателям.
- История с пагинацией, профиль, состояния загрузки и ошибок, мобильная навигация.
- Просроченная ссылка входа показывает сообщение и путь к восстановлению.
- CI с PostgreSQL 16: установка, production audit, Prisma generate/deploy, lint, typecheck, unit/integration, production build и Playwright.
- Настройки Vercel: Node.js 24, генерация Prisma Client перед сборкой.
- Документация запуска с нуля и обновления старой базы.

## Миграции

1. `202610080001_initial` — исходная схема для начала истории миграций.
2. `202610080002_accounts_and_sessions` — новые поля и индексы, снимки старых тренировок, перевод старых timed-подходов в секунды и выбор активной программы.
3. `202610080003_private_tables` — RLS и отзыв клиентских прав.

Во второй миграции есть вручную добавленные backfill SQL. Сохраняйте их при дальнейших изменениях. Для новой пустой базы достаточно `npm run db:deploy`. Для старой базы, созданной через db push, сначала backup, затем отметка initial как applied по README; не использовать migrate reset для нужных данных.

## Следующий этап — живой запуск

Код находится в main, но приложение ещё не опубликовано. Не нужно повторять первоначальную доработку: переходить к настройке сервисов.

1. Уточнить, создан ли уже проект Supabase. Последний запрос пользователю — создать проект и сообщить публичный Project URL. На момент этого снимка URL ещё не получен.
2. Настроить PostgreSQL и Supabase Email/Password Auth; для реальных писем нужен SMTP.
3. Заполнить DB/Auth/OpenRouter-переменные непосредственно в окружении и применить миграции.
4. Импортировать репозиторий main в Vercel, задать APP_URL и переменные до сборки, разрешить callback URLs в Supabase.
5. Пройти живой сценарий: health → регистрация и письмо → вход → стартовая программа → подход и перезагрузка → завершение и оценка → AI-программы на 1/3/7 дней → второй аккаунт → восстановление пароля.
6. Настроить backup, мониторинг health и бюджет AI.

### Переменные окружения

- `DATABASE_URL`: runtime; для Supabase serverless — Transaction pooler 6543.
- `DIRECT_URL`: Prisma CLI и миграции; direct connection или Session pooler 5432. Локально может совпадать с DATABASE_URL.
- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- `APP_URL`: точный production origin.
- `AUTH_DEMO_MODE=false` в production.
- `AI_PROVIDER=openrouter`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`.
- `AI_TIMEOUT_MS=90000`, `AI_DAILY_LIMIT=10` — исходные значения.

Секретные значения в этом файле отсутствуют. Пароли базы и секретные ключи добавляются непосредственно в окружение, без публикации в Git или переписке. Финансовый лимит OpenRouter настраивается отдельно от количества запросов приложения.
